Order intake schema - design review

A proposed PostgreSQL schema for the jacobian_hw order intake service, derived from SeniorPlatformTakehome.md: POST /orders, tenant-scoped GET /orders, strict tenant isolation, idempotent submission on (tenant_id, external_order_id). Every table lives in the order_service schema. It would ship as Flyway V2__orders.sql and V3__tenant_rls.sql after the comment-only V1__baseline.sql from PR #3, plus a 01-roles.sql init script for the three login roles (who connects as what). Nothing has been added to the repo.

Rounds 7-8: database users
  • Round 8: orders_admin_user can now write. It has INSERT/UPDATE/DELETE on the four service tables, plus default privileges so later tables get the same. It still can't write flyway_schema_history or run DDL. Its writes bypass RLS but are still bound by the FKs and CHECKs (verified).
  • Flyway runs as orders_owner, a new non-superuser role. It creates the order_service schema and owns every table, including flyway_schema_history. The app runs as orders_app. People run as orders_admin_user. The superuser (POSTGRES_USER) only runs 01-roles.sql once. See the table in who connects as what.
  • A trap I found while checking: with Spring Boot's @ServiceConnection (used today in PostgresTestConfiguration), spring.datasource.username is ignored. The app connected as the container's superuser, test, which bypasses RLS entirely. The tests must wire the users explicitly instead (verified below), and the dev compose profile has the same issue.
What changed in round 6, from your annotations and note
  1. Everything lives in the order_service schema. Setting spring.flyway.schemas=order_service makes Flyway create the schema and keep flyway_schema_history there. Hibernate uses default_schema=order_service. The DDL qualifies every name. Verified: validate passes, and the history table landed in order_service.
  2. New orders_admin_user role, created with BYPASSRLS. It sees every tenant's rows with no tenant set (verified despite FORCE). Round 8 added write access.
  3. orders.version is back (bigint NOT NULL DEFAULT 0, @Version Long). It gives optimistic locking again, and Persistable is no longer needed.
  4. The status CHECK is dropped. The column is still NOT NULL DEFAULT 'submitted', and the API alone decides which values are valid. Verified: the DB now accepts any text.
  5. Your question about database-generated ids: you're right, nothing stops it. App-side generation was a preference, not a constraint. I wanted the id before the INSERT, and Hibernate 6.6 has no UUIDv7 generator of its own. I've verified that Hibernate reads back a database default through @GeneratedValue(strategy = IDENTITY), so orders.id is now generated by the database (DEFAULT uuidv7()), like order_items.id (D1).
Earlier rounds:
  • The hash covers patient_id, order_type, priority, notes, and the sorted items. submitted_at, submitted_by, and item order are excluded.
  • The tenant comes from the JSON body on POST and the X-Tenant-Id header on GET.
  • Tenants and patients are read-only reference data; an unknown one gets a 422.
  • order_items has a uuid PK plus a (tenant_id, order_id) index.
  • order_type and priority are char(1) codes.
  • Ids are trimmed, and RLS ships.

At a glance

Shape
2 owned tables, 2 reference tables

All four live in the order_service schema. The service writes orders and order_items. It only reads tenants and patients, which other systems maintain. The submitter is copied onto each order.

Keys
UUIDv7 from the database

orders.id and order_items.id both come from DEFAULT uuidv7(). Hibernate reads the order id back to return in the 201. A patient's key is (tenant_id, id).

Idempotency
Unique key + request hash

UNIQUE (tenant_id, external_order_id) blocks duplicates. A SHA-256 of the order's content (submitted_at and submitter excluded) tells a replay (200) from a conflicting resubmission (409).

Isolation
3 layers, RLS included

The app filters by the request's tenant: the JSON body on POST, the X-Tenant-Id header on GET. Two composite FKs stop cross-tenant references. RLS on patients, orders, and order_items makes Postgres refuse cross-tenant access. This is ADR-001. Only orders_admin_user reads and writes across tenants.

Enums
char(1) codes; status text

order_type is L/I/M/C, priority is R/U/S, and status is submitted. The API keeps the words.

Deliberately left out
No auth, no reference writes, no extras

No credentials, no writes to tenants or patients, no status CHECK or history, and no partitioning.

How the tables relate

Dashed tables are read-only reference data. Every tenant-owned row carries tenant_id, and both child references include it: orders points at patients by (tenant_id, patient_id), and order_items points at orders by (tenant_id, order_id). Red rows hold PHI.

The write path, including duplicates

Everything happens in one transaction. First, the tenant and patient must already exist; the service never creates them. Then the unique constraint decides whether the order already exists, and request_hash decides how to answer a duplicate.

What request_hash covers (the idempotency ADR repeats this list)

The hash is computed over the validated, trimmed values in a fixed field order, with items sorted, not over the raw bytes. The stored line_no keeps the first submission's item order. Whitespace, JSON key order, and an absent vs null optional field don't change it, and neither does " PO-1 " vs "PO-1".

Retention

The assignment says external_order_id is "unique per tenant", which makes it a business key, not a short-lived retry token. So the key lives as long as the order, and there is no expiry to configure. A separate idempotency_keys table with a TTL would allow a second order with the same external_order_id once the key expired, which breaks that rule.

Still valid from earlier rounds

Replays insert nothing (INSERT 0 0). An unset tenant sees 0 rows, and after a transaction the setting reads '' (hence NULLIF). RLS rejects a write for another tenant, while the superuser bypasses it. Trimming CHECKs reject a leading space, a trailing tab, and a newline; length CHECKs fire. char(1) rejects whole words. Each CHECK's DETAIL echoes the full row, so set pgjdbc logServerErrorDetail=false. NUL is refused. The list and idempotency lookups use their indexes.
